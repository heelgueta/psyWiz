# Design

How the code is organised and the decisions behind it. Read this before
changing anything structural.

## One repository, two faces

A jamovi module is an R package with extra definition files, so psyWiz is both:

```
R/engine-*.R      the statistics; plain R, no jamovi dependency
R/print.R         console output for R users
R/jmv-*.R         shared jamovi glue
R/*.b.R           one thin R6 class per jamovi analysis
R/*.h.R, 00jmv.R  GENERATED by jmvtools from jamovi/*.yaml (committed, never edited)
jamovi/           analysis definitions (options, results, panels)
tools/            generators and build scripts
tests/testthat/   engine tests and headless jamovi tests
```

Rule: **no statistics in the jamovi layer.** A `.b.R` file turns options into
arguments of `invarianceWiz()` or `cfaWiz()`, caches the result and copies data
frames into tables. Anything a jamovi user can get, an R user can get.

## Engine

| File | Role |
|---|---|
| `engine-data.R` | `psw_prepare()`: validation, item type, row filtering, renaming |
| `engine-syntax.R` | `psw_syntax()`: lavaan syntax for each invariance step |
| `engine-fit.R` | `psw_fit()` and extraction of fit indices, loadings, reliability |
| `engine-invariance.R` | `invarianceWiz()`, `invarianceVerdict()`, score tests |
| `engine-multiest.R` | `cfaWiz()` |
| `engine-scale.R` | `scaleWiz()`: reliability, tau-equivalence ladder, Guttman / Mokken |
| `engine-esem.R` | `esemWiz()`: CFA against ESEM, correlations by scoring method |
| `engine-robust.R` | `invarianceMultiverse()`: verdicts across estimators and rules |
| `engine-composite.R` | `compositeWiz()`: rank-one check for formative indicators (no lavaan) |
| `engine-parallel.R` | `psw_run_tasks()`: sequential or parallel fitting |
| `plot.R` | `psw_figure()`: fixed-layout path diagram, variance tiles and comb plot (ggplot2) |

Decisions:

- **Internal names.** Items become `i1..ik` and factors `f1..fm` before
  anything reaches lavaan, and are translated back afterwards. jamovi variable
  names may contain spaces, accents or operators.
- **Explicit syntax instead of `group.equal`.** Every group's modifier is
  written out. This is what makes the Wu & Estabrook ladder possible, and the
  syntax shown to the user is exactly what was fitted.
- **Results are plain data frames.** lavaan objects are dropped unless
  `keep.fits = TRUE`, which keeps the cached jamovi state small.
- **Verdicts are separate from fitting.** `invarianceVerdict()` only reads the
  comparison table, so changing cutoffs is instant.
- **One fit-index version per table**, see METHODS.md.
- **Errors are sentences for users.** `psw_prepare()` catches the common
  problems (empty categories in a group, mixed item types, too few items)
  before lavaan produces something cryptic.

## Speed

A lavaan fit is single-threaded R code; making one fit use several cores would
mean rewriting lavaan's optimiser (in C++ or otherwise), which is out of scope.
What psyWiz parallelises is the set of independent models an analysis needs.

`psw_run_tasks()` with `parallel = "auto"` fits the first model in the current
process; if that took more than one second and at least two models remain, it
starts PSOCK workers (cross-platform) for the rest, otherwise it continues
sequentially. If workers cannot be started it falls back silently.

Measured on the development machine (16 cores, lavaan 0.6-21):

| Problem | Sequential | Automatic |
|---|---|---|
| Example data, ordinal ladder (8 items, 3 groups, 4 models) | 11 s | 7 s (3 workers) |
| 24 ordinal items, 3 factors, 4 groups, n = 4000, ladder of 4 models | 205 s | 145 s (3 workers) |
| Same data, single group, all 8 estimators | 19 s | 9 s (6 workers) |

In the large ladder each fit takes 17 to 48 s, so the parallel run is bounded
by the slowest fit plus the difference tests, which run in the main process.

Tried and rejected, or replaced:

- **Warm starts** (starting each step from the previous step's estimates): no
  measurable gain, because the time goes into sample statistics rather than
  optimisation, and `lavaan::modindices()` returned zeros for models fitted
  with `start = <fitted model>`.
- **`lavaan::lavTestScore()` for the score tests.** It inverts a bordered
  information matrix once per constraint: 248 s for one step of the large
  model above, and the first version of the ladder took 20 minutes because of
  it. `psw_score_uni()` computes the same univariate tests from a single
  inversion (1 s); a test checks that the numbers agree with lavaan.
- **Deciding on parallel fitting from the first model only.** With several
  estimators the first (ML) is often quick and later ones slow, so the switch
  is now made as soon as any fit is slow.

Still slow: modification indices for the ordinal intercepts step (about as
long as one fit), and the scaled chi-square difference test for large models
(about 15 s each above).

Not done yet: computing polychoric correlations and their asymptotic
covariance once and sharing them between the least-squares estimators in
`cfaWiz()`. It would help when run sequentially; in parallel the estimators
already overlap.

## Diagram

Automatic path-diagram layouts look bad because they must cope with any model.
psyWiz only fits simple-structure CFAs, so `psw_diagram()` uses one fixed
layout: factors in a column on the left, items in a column on the right, one
straight arrow per loading, correlations as arcs on the far left (up to four
factors), one panel per group or estimator. Arrow width encodes the
standardized loading, which makes panels comparable at a glance. Label space
is estimated from character counts for the image size given by
`psw_diagram_size()`; long names are truncated. If the model family grows
(cross-loadings, bifactor), this layout has to be extended deliberately, not
replaced by an optimiser.

## Colour

Off by default. In jamovi the only colour available in tables is red text
(`Cell.NEGATIVE`); the "Highlight" checkbox uses it for flagged step
comparisons (group analyses) and standardized loadings below .40
(multi-estimator), and colours weak loadings in the diagram. In R,
`print(x, colored = TRUE)` gives the red-to-blue ramp of the original
`cfawiz()`.

## jamovi layer

- **Run checkbox.** jamovi re-runs an analysis whenever an option changes.
  While `run` is off, `.run()` only validates the data and shows the plan.
- **Caching.** The engine result is stored as the state of the `fit` table.
  That table's `clearWith` lists exactly the options that require refitting;
  jamovi clears the state when one of them changes. Output options and
  cutoffs are not in the list. If you add an option that changes the models,
  add it there (for the group analyses: in `tools/gen_yaml.py`).
- **Generated yaml.** All analyses except Multi-Estimator CFA get their
  `.a/.r/.u.yaml` from `tools/gen_yaml.py`, because they share option blocks
  (item treatment, estimator, decision criteria, figure options) and table
  layouts. The two group analyses also share their R implementation
  (`R/jmv-invariance.R`).
- **Second cache.** The robustness check stores its result as the state of
  its own summary table, cleared only by the model, the grouping variable
  and `strict` (it spans estimators and item treatments itself).
- **Dynamic columns** (one per group or per estimator) are added in `.init()`,
  where jamovi expects the table structure to be defined.

## Decisions taken with the author (2026-11-14)

- Three menu entries (one-factor, correlated factors, multi-estimator) even
  though the first two share an implementation: easier to find for beginners.
- Factor boxes, not lavaan syntax. A syntax box and bifactor models come later.
- On a failed step: report and point at the worst constraints; no automatic
  partial invariance.
- Verdict with flags against editable cutoffs, source cited.
- Multi-estimator comparison is single-group only in this version.
